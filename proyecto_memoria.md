# Memoria Técnica - Comanda

Este documento sirve como registro central de decisiones arquitectónicas, estructura del modelo de datos y cambios importantes en el sistema.

---

## 1. Arquitectura General del Sistema

El sistema utiliza una arquitectura cliente-servidor con comunicación bidireccional en tiempo real para coordinar al cliente, la cocina y la caja.

```
                      +-------------------+
                      |   Servidor Node   |
                      | (Express/Sockets) |
                      +---------+---------+
                                |
        +-----------------------+-----------------------+
        |                       |                       |
+-------v-------+       +-------v-------+       +-------v-------+
|  Cliente (QR) |       | Cocina Screen |       | Mostrador UI  |
| (Mobile View) |       | (Order Board) |       |  (Dashboard)  |
+---------------+       +---------------+       +---------------+
```

### Organización del backend
* **`domain.js`**: reglas de negocio (estado de mesas y pedidos, validación de payloads, habilitación, cobro, llamados al mozo) como funciones sin estado global ni dependencias de sockets o SQLite. Reciben por argumento lo que necesitan (la mesa, sus pedidos activos, el menú) y tienen unit tests en `domain.test.js`.
* **`server.js`**: transporte. Express y Socket.io, autenticación, estado en memoria (`tables`, `orders`, `menuCache`), y por cada evento: buscar el estado, llamar al dominio, persistir y emitir.
* **`auth.js`**: sesiones de personal (revocables, sin vencimiento automático; ver Decisión 9), freno de intentos de login y comparación de contraseñas en tiempo constante (unit tests en `auth.test.js`).
* **`db.js`**: persistencia SQLite (esquema, migraciones, prepared statements).

### Tecnologías Utilizadas
* **Backend**: Node.js, Express, Socket.io.
* **Frontend**: React (Vite), Vanilla CSS (Modo oscuro y temas cálidos/glassmorphism), Lucide Icons.
* **Comunicación**: HTTP (para carga inicial del menú) y WebSockets (para actualizaciones de pedidos y mesas en tiempo real).

## 2. Modelos de Datos (en memoria, respaldados por SQLite — ver Decisión 4)

### Mesas (Tables)
Cada mesa tiene un estado que determina qué puede hacer el cliente y qué se muestra en la caja.
```typescript
interface Table {
  id: string; // Número de mesa (e.g., "1", "2")
  status: 'libre' | 'pedido_pendiente' | 'comiendo' | 'esperando_cuenta' | 'pagando_tarjeta' | 'cuenta_cerrada';
  currentOrderId: string | null;
  paymentMethod: 'efectivo' | 'tarjeta' | null;
  total: number;
  qrToken: string; // Secreto del QR de la mesa (Decisión 6). Solo lo reciben el mostrador y la propia mesa.
  enabled: boolean; // Habilitada para pedir (Decisión 7). Una mesa bloqueada siempre está vacía.
  blockOnClose: boolean; // Bloqueo pedido con clientes sentados: se aplica al cobrarla.
}
```

### Pedidos (Orders)
```typescript
interface OrderItem {
  productId: string;
  name: string;
  price: number;
  quantity: number;
}

interface Order {
  id: string;
  tableId: string;
  items: OrderItem[];
  status: 'pendiente' | 'en_preparacion' | 'listo' | 'entregado' | 'cancelado';
  archived: boolean; // true cuando la mesa se cobró (close-table) o el mostrador canceló el pedido
  createdAt: string; // ISO String
  notes?: string;
}
```
`status` es el flujo de cocina; `archived` es independiente y decide si el pedido cuenta para el
total/ticket del mostrador. Un pedido puede estar `entregado` (cocina ya lo sirvió) sin estar
`archived` todavía (la mesa no pagó) — por eso cocina filtra por `status` y mostrador por `archived`.

### Menú (Menu)
Administrable desde el Mostrador y persistido en SQLite (tabla `menu`); los 13 productos originales son solo la semilla del primer arranque.
```typescript
interface MenuItem {
  id: string; // 'm1'..'m13' de semilla; 'm-{timestamp}-{rand}' para altas del mostrador
  name: string;
  description: string;
  price: number;
  category: 'bebidas_calientes' | 'bebidas_frias' | 'pasteleria' | 'salado'; // fijas en v1 (los filtros del cliente están atados a ellas)
  image: string; // Nombre identificador para iconos ('coffee' por defecto en altas)
  available: boolean; // false = "Agotado": visible pero no pedible (rechazado también server-side)
}
```

## 3. Historial de Decisiones Técnicas
* **Decisión 1**: Almacenamiento en Memoria Volátil. Se decide no usar una base de datos física para la primera versión para simplificar la ejecución local. Toda la información se mantendrá en memoria RAM en el servidor de Node.js. *(Superada el 2026-07-02 por la Decisión 4: el estado ahora se persiste en SQLite.)*
* **Decisión 2**: Enrutamiento simple basado en Query Parameters en el frontend (`?view=client&table=X&t=<token>`, `?view=kitchen`, `?view=counter`). Esto permite que un único build sirva para los tres propósitos y facilita la simulación del código QR (ejemplo: `http://localhost:5173/?view=client&table=5&t=<token>`; el token se ve en el Mostrador, ver Decisión 6).
* **Decisión 3**: Sistema de Audio Sintético. Para no depender de archivos mp3 externos que puedan fallar en la carga local, el sistema utiliza la API Web Audio de JavaScript para sintetizar tonos de campana (`chime` y `double beep`) para notificar al cajero y cocineros.
* **Decisión 4**: Persistencia con SQLite embebido (`node:sqlite`, incluido en Node >= 22.13) bajo un patrón write-through: la memoria sigue siendo la copia de trabajo sobre la que opera toda la lógica de negocio, y cada mutación se refleja en disco de forma sincrónica. Se eligió el módulo nativo de Node (y no `better-sqlite3` ni Postgres/Mongo) para no agregar dependencias externas ni infraestructura: para el volumen de una cafetería alcanza de sobra. Los `items` de cada pedido se guardan como columna JSON (siempre se leen/escriben en bloque junto al pedido, `sanitizeItems()` ya garantiza su estructura; una tabla `order_items` separada solo agregaría joins sin ninguna consulta que lo justifique hoy). Los tokens de sesión de staff se quedan en memoria a propósito: re-loguearse tras un restart no es pérdida de datos, y persistir tokens en disco sería un riesgo de seguridad innecesario.
* **Decisión 5**: Un pedido enviado a cocina no se modifica desde la mesa: cada ronda del cliente es una comanda nueva (`new-order`), y la cuenta de la mesa suma todos sus pedidos activos. Se eliminó `update-order`, que mezclaba items en el pedido activo aunque cocina ya lo estuviera preparando o lo tuviera listo. Las correcciones por error humano siguen siendo del Mostrador (`edit-order`/`cancel-order`, solo con el pedido `pendiente`).
* **Decisión 6**: Cada mesa tiene un token secreto en su QR (`?table=X&t=<token>`), y la conexión del cliente queda atada a la mesa en el `join`. Sin el token de la mesa no se entra a su sala (no se ven sus pedidos), y `new-order`, `request-bill` y `request-assistance` usan la mesa de la conexión, nunca el `tableId` que manda el navegador. Se eligió sobre la alternativa simple (atar al `join` sin token), que frenaba que una pestaña actuara sobre otra mesa pero dejaba entrar a cualquiera escribiendo `?table=7` en la URL. El token se conserva al cobrar la mesa (el QR impreso sirve para los próximos clientes) y cambia solo si el Mostrador lo regenera o la mesa se da de baja y se vuelve a agregar.
* **Decisión 7**: Las mesas se habilitan y bloquean desde el Mostrador. "Iniciar Día" habilita todas y "Cerrar Día" bloquea todas a la vez; en el medio, cada mesa se maneja por separado. Una mesa bloqueada no acepta pedidos ni llamados al mozo, así que un link filtrado no sirve fuera del horario ni en una mesa que el Mostrador cerró. Regla clave: **una mesa bloqueada siempre está vacía**. Si estuviera bloqueada con una cuenta abierta, el próximo que escaneara el QR al habilitarla vería la cuenta del anterior, y el Mostrador no distinguiría una mesa cerrada de una con clientes. Por eso bloquear una mesa con clientes (o cerrar el día con mesas ocupadas) no la corta: la marca (`blockOnClose`) y se bloquea al cobrarla, o en el momento si el Mostrador cancela todos sus pedidos. Cerrar el día y cerrar la caja son independientes: el cierre del día ofrece cerrar la caja, pero no es obligatorio. Al cobrar una mesa, el server desconecta a todos sus celulares y el cliente ve "Gracias por tu visita"; sin eso, un celular olvidado con la página abierta seguiría viendo los pedidos del grupo siguiente. Se eligió sobre habilitar la mesa en cada visita, que protege más pero obliga al personal a abrir cada mesa al sentar a los clientes.
* **Decisión 8**: Las reglas de negocio viven en `backend/domain.js`, separadas del transporte (`server.js`) y la persistencia (`db.js`), y se prueban con unit tests (`node:test`, sin dependencias). Antes estaban mezcladas con los handlers de sockets y leían el estado global del módulo, así que solo se podían probar con E2E de Playwright: lentos, con servers levantados y mesas repartidas entre specs para no pisarse. Las funciones del dominio modifican en el lugar la mesa que reciben, como hacía `server.js`: es el mismo objeto que después se persiste y se emite, y devolver copias obligaría a reemplazarla en el array de mesas en cada evento. Los E2E siguen cubriendo los flujos completos y la seguridad del transporte (tokens, roles, salas).
* **Decisión 9**: Las sesiones de personal no vencen solas; se revocan con logout, con "Cerrar Otras Sesiones" desde el Mostrador o al reiniciar el server (que es lo que pasa al cambiar las contraseñas). Se descartaron tres alternativas. (1) Vencimiento fijo a las 12 h del login: en un local de horario corrido corta la pantalla en pleno servicio, a una hora que depende de cuándo se inició sesión, y en cocina los pedidos nuevos dejan de verse hasta que alguien nota el login. (2) Revocar todas las sesiones al terminar el día: el corte sería predecible, pero obliga a tipear la contraseña cada mañana en varias tablets (que termina en un post-it pegado a la tablet). (3) Vencimiento por inactividad: limpia tokens olvidados, pero suma una regla poco visible para un beneficio chico. Con una contraseña compartida que conoce todo el personal, quien tiene un token copiado casi siempre sabe también la contraseña, así que acortar las sesiones protege poco; lo que corta de verdad a un ex-empleado o a una tablet perdida es revocar todo (el botón) y, si hace falta, cambiar la contraseña. Si en algún momento hace falta saber quién hizo cada cosa, lo que corresponde son usuarios por empleado, no sesiones más cortas.
* **Decisión 10**: Ante un error en un handler de socket (típicamente una escritura en SQLite que falla), la memoria se rehace desde la base (`reloadFromDb`) en vez de deshacer cada mutación a mano. Los handlers mutan la memoria antes de persistir, así que sin esto una escritura fallida dejaba al server mostrando y cobrando un estado que la base no tenía; y como Socket.IO no atrapa los errores de los handlers, en la práctica tiraba abajo el proceso. La base es la fuente confiable: la transacción vuelve atrás, y los avisos a las pantallas salen siempre después de persistir, así que ninguna llegó a ver el estado descartado. Se descartó hacer cada handler transaccional sobre copias (calcular el estado nuevo, persistir y recién ahí reemplazar): es más preciso pero obliga a reescribir todos los handlers y el dominio, que modifica en el lugar a propósito (Decisión 8). El wrapper `on()` envuelve todos los eventos y, si el evento esperaba acknowledgement, responde `{ ok: false, error: 'server_error' }`.
* **Decisión 11**: Las fotos de productos y el logo se guardan **dentro de SQLite** (tabla `images`, columna BLOB), no en una carpeta del disco. Para una instalación por local, la base pasa a ser lo único que hay que respaldar y restaurar, y en hostings con disco efímero (Render) no se pierden imágenes que la base sigue referenciando. El costo (la base crece) es chico porque el navegador achica cada imagen antes de subirla (800 px en JPEG las fotos, 400 px en WebP el logo, para conservar la transparencia) y el server acepta hasta 300 KB, verificando los primeros bytes de cada formato y no solo el mime declarado. Una imagen que deja de usarse (foto reemplazada, producto borrado, logo cambiado) se borra en el momento, y las que se subieron sin asignarse se limpian al arrancar. Se descartó guardarlas en un servicio externo (S3, Cloudinary) para no sumar cuentas ni credenciales por local.

## 4. Guía de Ejecución y Pruebas Locales

Para iniciar la aplicación en tu entorno local:

1. **Servidor Backend**:
   - Ir a la carpeta `backend/`
   - Ejecutar `npm run dev` para iniciar el servidor de WebSockets en el puerto `3001`.
2. **Cliente Frontend**:
   - Ir a la carpeta `frontend/`
   - Ejecutar `npm run dev` para iniciar el servidor de desarrollo Vite en el puerto `5173`.
3. **Simulador General**:
   - Abrir `http://localhost:5173/` en el navegador.
   - Desde el panel principal se pueden abrir múltiples pestañas para simular diferentes mesas (clientes) y las pantallas del mostrador y cocina interactuando simultáneamente.
   - Las mesas arrancan bloqueadas: en el Mostrador, "Iniciar Día" las habilita.
   - Los links de las mesas llevan su token. El portal los pide a `/api/demo/table-links`, que solo existe con `DEV_MODE=1` (lo setea `npm run dev`) o en la demo pública; si no, cada link se abre desde el botón de QR de la mesa en el Mostrador.

Las demás mesas conservan su número al quitar una del medio (clave: los QR impresos apuntan a `?table=X`). Cambios acompañantes: `new-order` ahora rechaza pedidos de mesas inexistentes (antes creaba el pedido igual y solo salteaba la mesa — con QRs viejos de mesas dadas de baja eso pasaba de rareza teórica a pedido huérfano que cocina prepararía para nadie); el `join` a una mesa inexistente responde `table-state: null` y `ClientView` muestra una pantalla de "Esta mesa no está disponible" en vez de quedarse muda dejando pedir a una mesa fantasma (también reacciona en vivo al evento `table-removed` si la mesa se elimina mientras el cliente la mira). `/api/test/reset` sigue restaurando exactamente las 12 mesas iniciales. Suite completa (4 specs) en verde; verificado además que altas/bajas sobreviven al restart del server.

Ahora la calcula el server desde la DB y el navegador solo la muestra. Se descartó un primer enfoque que tenía tres fallas: (1) sin migración de esquema, el `INSERT` con la columna nueva rompía las bases existentes; (2) sumaba por `created_at` (fecha de *creación* del pedido, en UTC) en vez de por fecha de *cobro* — una mesa que pidió 23:50 y pagó 00:10 caía en el día equivocado, y en Argentina (UTC-3) el "día" cambiaba a las 21:00; (3) contaba pedidos cancelados como ventas (filtraba solo por `archived`). Implementación final: columna `orders.closed_at` (con migración `ALTER TABLE` con guarda vía `PRAGMA table_info`, la primera del proyecto) que `close-table` sella con el momento del cobro; `getDailySalesTotal()` suma pedidos `entregado`+`archived` con `closed_at >=` medianoche **local** del server (los items se suman en JS desde el JSON — un puñado de filas por día, sin denormalizar un `total` que pueda divergir); sin columna `total` extra. De paso se corrigió una rareza preexistente de `close-table`: pisaba a `entregado` los pedidos ya cancelados de la mesa (ahora los cancelados quedan `cancelado` y nunca cuentan para la caja). El valor viaja en `/api/initial-state` (carga/recarga) y en el broadcast nuevo `daily-sales-updated` tras cada cobro — el server es la única fuente: `CounterView` ya no suma nada localmente, y dos pestañas de mostrador abiertas ven el mismo número. Cubierto en `tables.spec.js` (cobro → $1800 → recarga → sigue $1800); suite completa en verde y migración verificada contra una base creada con el esquema anterior. Limitación conocida: "hoy" es la medianoche del reloj del server, no hay concepto de turno/cierre de caja manual. *(Resuelta el mismo día con el cierre de caja manual, ver siguiente entrada.)*
  - **Cierre de caja desde el Mostrador**: botón "Cerrar Caja" en el header del panel (evento `close-register`, solo rol `counter`, con confirmación). Cada cierre queda registrado en la tabla nueva `register_closures` (`closed_at`, `total`, `orders_count`) como histórico de arqueos, y la "Caja del Día" pasa a significar *lo cobrado desde el último cierre* (si nunca hubo cierres, desde la medianoche local — el comportamiento anterior). Decisiones: cerrar caja **no** exige mesas libres — lo que se cobre después del cierre cuenta para la caja siguiente, así una mesa que se queda hasta tarde no bloquea el arqueo del turno; y si el último cierre fue ayer, lo cobrado después entra en la caja de hoy (la plata que no entró en un arqueo entra en el siguiente, nunca se pierde).
